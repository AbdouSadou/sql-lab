# SQL playground for teaching

A static, browser-only SQL playground for teaching. SQLite runs in your browser as WebAssembly: there is no server, no account and no analytics, and the queries and data you work with never leave the browser. The page is plain HTML, CSS and JavaScript. Two things are built, and both are committed, so there is nothing to build to run or deploy the site: the code editor's bundle, `vendor/editor.js`, and the app page's own scripts and stylesheets joined into one file each, `bundle/app.js` and `bundle/app.css`.

Based on SQLime by Anton Zhiyanov (https://github.com/nalgeon/sqlime).

## Features

- Full SQLite (CTEs, window functions, views, triggers) in the browser. Run with Ctrl/Cmd+Enter.
- A code editor (CodeMirror 6): SQL highlighting, line numbers, bracket matching, and suggestions as you type for SQLite's keywords and functions and the open database's tables, views and columns (Ctrl+Space shows them at any time; the arrow keys pick one and Enter takes it, and until one is picked Enter starts a new line). Ctrl/Cmd+/ comments or uncomments the line. Tab indents; Escape, then Tab, leaves the editor. If the editor's script cannot load, a plain editor takes its place and everything still works.
- An app-like layout: a top bar, a sidebar with Schema, Exercises and History tabs, the query above its result, and a status bar. The sidebar's width, whether it is hidden and the editor's height are set by dragging the bars between the panes (or with the arrow keys) and kept between visits.
- On a tablet or a narrow window (700 to 1099 px wide) the sidebar opens over the page from the Sidebar button at the top, and closes with its Close button, Escape or a press beside it. On a phone (under 700 px, or held sideways) the query and its result are two views, Editor and Result, and running a query shows its result; Copy link, Export, Theme and Help are in the More menu (the three dots), and Run (with Check answer in an exercise) is in a bar at the bottom of the screen.
- A text size for a projector: A− and A+ at the right of the toolbar above the editor make the SQL and the results smaller or larger, from 12 to 24 px, and the size is kept. At 1280×720 and 20 px a six-line query and six result rows fit on the screen.
- Built-in datasets, listed in `datasets/manifest.json` and chosen from the database menu in the top bar (the button showing the open database). The default one (Home Store) is open on a first visit. `?db=<id>` in the address opens a dataset directly. Nothing runs on its own: until the first Run the result area offers up to three sample queries (the manifest's, or the first table's rows), and choosing one puts it in the editor without running it. A database that is loading shows its name, its size and a progress bar.
- The Schema tab: tables and views with their columns, types, key marks and row counts. Clicking a name puts it in the editor.
- Open a SQLite database file, a SQL script, or a database from a URL (Open from URL asks for the address in a small dialog), all three from the database menu, and export the open database, with your changes, as a file (Export, then Database (.db)…; the file name given there also renames the database).
- Results are a ruled table: numbers right-aligned in even figures, NULL in grey italics, the column names on a header that stays in view, at most 500 rows ("Showing 500 of N rows"), and the time taken. A value longer than 60 characters is cut, and pressing it shows all of it. A statement that returns no rows says "Done", with how many rows it changed. A failed run shows SQLite's message as it is and quotes the statement that failed; a run that takes longer than 300 ms says "Running…". Download CSV (beside the result, and Export, then Results (.csv)) saves the whole result.
- Share a query with Copy link in the top bar: the link holds the dataset, the exercise (if one is open) and the SQL, compressed, in the part of the address after `#`, which browsers never send to a server. A short message at the bottom of the page says "Link copied" (exports and opening a database are confirmed the same way); if the browser keeps the clipboard to itself, the link appears under the button, ready to copy. Opening a link puts the SQL in the editor without running it. A link can be long for very large queries.
- Exercise sets with a Check answer button (Ctrl/Cmd+Shift+Enter), a numbered list of exercises with pass marks, hints shown one at a time ("Show hint (1 of 3)"), Previous and Next, and a "7 of 10 complete" counter kept in your browser. Pick a set in the Exercises tab, or open `?set=<set id>` (add `&ex=<exercise id>` for one exercise). Check runs the query, then says at the top of the result whether it is right: "Correct. 5 rows match." with a Next exercise button, or "Not quite." with what differs; when a row differs, the expected rows and the student's are shown side by side, with the cells that differ outlined.
- A run log: every Run is kept (the last 200 per dataset, fewer if the queries are very long, in that browser on that device) and the History tab lists it, newest first; a click puts an earlier query back in the editor. Its times are UTC. When the browser has no room left to keep the log or the exercise progress, a notice above the result says so.
- Evidence export: Export, then Evidence (.txt)…, saves the run log as a `.txt` file with the student's number and a checksum, to attach to assessed work; `verify.html` checks such a file. The file holds the log of the open dataset only (an uploaded file has a log of its own), so a student who worked on two datasets exports once for each dataset. The log lives in one browser profile: on a shared lab PC whose profile is wiped at log-off, or in a private window, it is gone, so students should export before they log off. `about.html` tells them this, and tells markers about `verify.html`.
- Nothing moves when the device asks for reduced motion (the menus, popovers, messages and the tick of a correct answer appear at once).
- Browsers: current Chrome, Edge, Firefox and Safari. The menus use the `popover` attribute, so they need Safari 17, Firefox 125 or Chrome 114 or later; an older browser shows the page without them.
- Kept in the student's own browser (`localStorage`) and nowhere else: the last query for each database, exercise progress, the SQL last written for each exercise, the run log, the theme the student chose, the text size (`sqllab.textSize`) and the pane sizes (`sqllab.layout`).
- Light and dark themes: the page follows the device until the student picks Light, Dark or Match device in the Theme menu.

## Adding a dataset

A dataset is a `.db` file in `datasets/` plus one entry in `datasets/manifest.json`: `id` (letters, digits, `_` or `-`, at most 64; it goes into share links, exercise sets and the name of the run log), `name` (shown in the menu), `file` (a relative path such as `datasets/northlight_retail.db`), an optional `description`, an optional `samples` list (up to three `{"label": "...", "sql": "..."}` sample queries offered before anything has run; without it the first table's rows are offered; a sample that is not two pieces of text is left out with a warning in the browser's console), and `"default": true` on exactly one entry. The file must be a SQLite database (its first bytes are checked). A manifest that breaks these rules is reported on the page with the specific reason. Renaming an `id` later breaks the exercise sets that name it and orphans students' saved run logs, so choose ids once.

The tests are written against Northlight Retail (`northlight`), which the published exercise set uses too, so keep it in the manifest; any entry can be the default. A few tests follow the manifest as it is, so after editing it run the tests and update them on purpose: the manifest test and the first-visit tests in `tests/m3-datasets.spec.js` (the AC1 ones expect the default, today Home Store with 200 orders), and the database menu's screenshots, which show every dataset with its description and size (`npx playwright test tests/ui-visual.spec.js --project=chromium-root -g menu-database --update-snapshots`, then look at the new pictures).

## Adding an exercise set

An exercise set is one file, `exercises/<set-id>.json`. Commit it and nothing else: there is no list to edit, no manifest entry and no build step. The file name must equal the `id` inside it (`store-basics.json` holds `"id": "store-basics"`), and the id uses only letters, digits, `_` and `-` (at most 64), because it goes into links and into the name of the browser's progress record. `dataset` is the id of a dataset in `datasets/manifest.json`; opening the set loads that dataset. Changing an exercise's `id` later makes browsers forget that exercise's pass mark and saved SQL. Each set is one more file that every first visit asks for, since the page reads them all to fill the Exercises menu; that is nothing for a handful of sets, and worth a thought before adding dozens (see [The app bundle](#the-app-bundle) for why the number of requests matters).

```json
{
  "id": "store-basics",
  "title": "Northlight stores — a first look",
  "dataset": "northlight",
  "exercises": [
    {
      "id": "s01",
      "title": "West Yorkshire stores, oldest first",
      "prompt": "List the name and opening date of every store in the West Yorkshire region, the longest-established first.",
      "hints": ["Filter with WHERE.", "Sort with ORDER BY."],
      "model_query": "SELECT store_name, opened_date FROM stores WHERE region = 'West Yorkshire' ORDER BY opened_date;",
      "order_matters": true,
      "check_column_names": false
    }
  ]
}
```

Exercises are SELECT-only. `hints` are revealed one at a time, in order. A student's query passes when its result equals the model query's result on the original dataset: column count always, column names only with `"check_column_names": true`, and the row order only with `"order_matters": true` (the default compares the rows as a multiset). The model query is never shown on the page, but it is in the file the browser fetches, so a student who opens the developer tools can read it: this is for practice, not for assessment.

A `model_query` that fails, or a `dataset` that does not exist, is not caught when the Exercises menu is built (the menu checks only the file's shape): the dataset is reported only when the set is opened, and the model query only when an exercise is checked, when the student is told that the exercise cannot be checked and the browser's console says why (the engine's message, which can name a column or a table of the query but does not contain the query). So an instructor should try each new exercise once: open the set and press Check on every exercise before publishing it.

How the site finds the sets: the page reads the folder listing of `exercises/`. `python3 -m http.server` writes one itself, and the Pages workflow writes `exercises/index.html` while it stages the site (the step "List exercise sets" in `.github/workflows/pages.yml`), because GitHub Pages cannot list a folder. A file that is not valid still appears in the Exercises tab's set menu, greyed out and named after its file, with the problem under its name, so you see it at once. Progress and the SQL a student last wrote for each exercise are stored in the student's own browser (`localStorage`), one record per set; the Reset progress button clears them (it does not clear the run log).

## Deploying

Pushing to `main` redeploys the site: `.github/workflows/pages.yml` copies the repository root, leaving out `tests/`, `docs/`, `tools/`, `node_modules/`, `package.json`, `package-lock.json`, `playwright.config.js` and the git files, and publishes it with the official GitHub Pages actions. Everything else at the root is public, `datasets/generate_db.py` and `CODEMAP.md` included. The workflow can also be started by hand from the Actions tab. It compiles none of the site's code and runs no test (it only writes the exercise listing, the link previews and the web manifest into the copy it publishes): the two built parts, `vendor/editor.js` and `bundle/`, go out as committed, so after a change to `js/` or `css/` push the rebuilt `bundle/` with it ([The app bundle](#the-app-bundle)).

While it stages the site the workflow also writes what a shared link's preview shows (the Open Graph tags: the page's title and description, and a picture, `img/social.png`) and a web manifest (`site.webmanifest`, with the app's icons) into the staged pages, with `node tools/site-meta.mjs` (step "Link previews and web manifest"). A preview needs the site's absolute address: `SITE_URL` in `js/lab/config.js` when it is set, else the address GitHub Pages gives the workflow. The pages in the repository carry no address and no app name; the tags are written only into the copy that is published.

Once, per repository: Settings, Pages, Source must be set to GitHub Actions. Until it is, the workflow fails or publishes nothing. The site is then at `https://<user>.github.io/<repo>/`. All addresses in the code are relative, so it works under that subpath; `.nojekyll` must stay at the root.

The evidence export and `verify.html` need a secure page (https, or `localhost`): browsers withhold the checksum function otherwise. GitHub Pages is https.

## Marking evidence files

A student exports their run log from the Export menu in the top bar (Evidence (.txt)…): they type their student number, and the browser saves `evidence-<dataset id>.txt`. To check one:

1. Open `verify.html` on the site (for example `https://<user>.github.io/<repo>/verify.html`). The app itself does not link to it; the About page does, in its "For markers" section, and you can bookmark it.
2. Paste the text of the student's `.txt` into the box, or drop the file on the page, or choose it. The page checks it at once; nothing is uploaded.
3. Read the result. **VALID** shows the student number, the number of queries, the time of export and the dataset. **EDITED** says why: the checksum does not match, or the footer is missing or damaged. A file covers one dataset only (the `dataset:` line): for work on two datasets, ask for two files.
4. To re-run a query, click the `link:` line under an entry in the `.txt` (or paste it into the address bar). The dataset opens with that SQL in the editor; press Run. The link points at the address the student was using, and entries that failed, or that came from an uploaded or URL database, have none.

An evidence file is corroboration, not proof: the checksum shows that a file was not changed after it was exported, but the code is public and runs on the student's machine, so a determined student can fabricate a file.

The query count is the number of entries the exporter wrote. SQL is written to the file as it was run, except that a line of it that looks like an entry header (`[4] 2026-11-09T13:58:12Z · 1 row`) gets a backslash in front, so that SQL cannot add entries to the count; the entry's `link:` still holds the exact SQL.

## Settings

All three are in `js/lab/config.js`:

- `APP_NAME` (default "SQL Lab") is the one place the app name is written; page titles, headers, footers, the link preview, the web manifest and the first line of an evidence file take it from there. The tests spell the current name out, so after renaming, update them (`grep -rn "SQL Lab" tests/`). The picture a shared link shows, `img/social.png`, has the name drawn in it: redraw it, with the favicons, by `node tools/build-favicons.mjs` (it needs the test tools below). Evidence files exported under an older name still verify.
- `STUDENT_ID_PATTERN` (default `^[A-Za-z0-9]{6,12}$`) is the format the evidence dialog accepts for a student number. Change `EVIDENCE_HINT` and `EVIDENCE_INVALID_MESSAGE` beside it so the wording matches. `verify.html` does not apply the pattern, so files exported under an older pattern still verify.
- `SITE_URL` (empty by default) is the site's public address, for example `https://sql.example.org/` for a custom domain. A link preview needs an absolute address for its picture; while `SITE_URL` is empty the deploy uses the address GitHub Pages gives (`https://<user>.github.io/<repo>/`), so set it only when the site lives somewhere else.

### Features that are still switched off

The import and export work described in `docs/SQL Lab Assessment Workflow Plan.md` is being built in phases, each behind a flag that is off until you turn it on. The flags are in `js/lab/config-workflow.js` (`PREVIEW_FLAGS`): set one to `true`, rebuild the bundle (`npm run build:app`) and commit, and the feature is on for everyone. Before a flag goes on for everyone, other places have to be brought up to date as well (About, this README's section on marking evidence files, the evidence dialog's line): the plan's section 8, "Before a flag is switched on for everyone", lists them. To try a feature yourself first, add its name to the address for one visit: `index.html?preview=import`, or several with commas, `?preview=import,export`. So far three features are behind a flag:

- `import` (the plan's Phase 2): with `?preview=import`, "Open a file…" and `Ctrl+O` also take CSV files (`.csv`, `.tsv`, `.txt`), several at once, and files dropped on the page are taken as if they had been chosen. A dialog shows the first rows of each file exactly as read, with the settings it found (delimiter, text encoding, the row of column names), and nothing is imported before Import is pressed. Each file becomes a table, into a new database or into an opened one (never into a course database); nothing in a file is cleaned. When the import ends, the results pane shows a report (each column's type, its blanks, and what stopped a mostly-numeric column being a number, and the table and column names that SQL keeps for itself, such as `Order`, which a query must write in double quotes), and the evidence file lists the import. With `import` alone an Excel workbook is refused with a message; `excel-import` (next) takes workbooks. Until autosave is built (the plan's Phase 4), an imported database is lost on a reload, as an opened file is: weigh that before switching `import` on for students.
- `export` (the plan's Phase 3): with `?preview=export`, the Export menu (and the More menu on a phone) has "Tables as CSV…" after "Database (.db)…".
  - What a student sees: a dialog lists every table and view of the open database with its row count and a tick box; nothing is ticked at first, except when the database has only one table or view. One table is saved as one `.csv` file, named after it; two or more are saved together as one `.zip` file named after the database (`sales.db` gives `sales-tables.zip`), with a `.csv` file for each. Every row is exported, and the zip tool (fflate) is fetched only when Export is pressed with two tables or more. Cancel and Escape stop an export and nothing is saved; so does a table that cannot be read to its end (a view can count and then fail). The evidence file lists each export that saved a file (its name and size, and each table with the rows written).
  - What is in a file: UTF-8 with a byte-order mark, so that Excel reads it correctly, with the column names on the first row (for a view with two columns of one name, the names the engine gives: `a`, `a:1`); a value that is empty text and a NULL are both written as an empty field, and a BLOB is written as `x'…'` with its bytes in hex, as the results pane shows one (the dialog says so when it happens). Texts are written as stored, except that a byte that is not valid UTF-8 comes out as U+FFFD (a NUL is kept). A text that starts with `=`, `+`, `-` or `@` is not made safe for a spreadsheet, which may read it as a formula. A table of one column does not come back whole from an import: a row whose only value is NULL or empty is written as an empty line, and the import skips empty lines (writing `""` instead would keep those rows; the owner agreed to leave it as built, and the plan's section 5 says so).
  - Limits, to weigh before switching `export` on for students, as for `import`: the file is built in the page's memory, so a very large table can fail on a small computer; a zip of more than 65,535 files or 4 GiB is refused with a message; one slow count, or one slow step of a heavy view, cannot be interrupted, and every view is counted when the dialog opens, so a heavy view can hold the page for seconds before the student has chosen anything (if a student stops the script from Firefox's bar while an export is reading a heavy view, the page is expected to stay busy until it is reloaded, which was reasoned and not tried, and a reload loses an imported or opened database); the export reads what the database holds at that moment, uncommitted changes included, so a file can hold rows that are rolled back later; a key or a press that reaches the page after the last piece has been written comes too late (the file is saved, and the message and the evidence file say that it was); and the page cannot know whether the browser kept the file, so a student who dismisses the box for saving still sees "Exported" and has the event.
  - Looked at by hand by the owner on Nov 18, 2026: a real phone, an exported file opened in Excel, and a zip opened by Windows itself. Not yet looked at by hand, and to be before `export` is switched on for students: an exported CSV and zip opened in Tableau, Safari, a lab PC, `con.csv` on Windows, the dialog with a screen reader, and a table of about a million rows on a lab PC (the plan's section 9 lists them all).
- `excel-import` (the plan's Phase 5): with `?preview=import,excel-import`. It needs `import`: `?preview=excel-import` alone does nothing, as if no flag were given. The owner has not yet looked at any of it by hand or decided on any of what the build chose beyond the plan; the plan's section 3 lists each of those choices ("As built (Phase 5, Nov 19, 2026)"), and each can be changed.
  - What a student sees: an Excel workbook (`.xlsx` or `.xls`, or a web page or an XML spreadsheet saved under one of those names: what a file is, is decided from its first bytes) is chosen or dropped with the other files, and the description of the "Open a file…" entry and the message for a mixed choice say "CSV and Excel files". A workbook of two sheets or more has a second row of tabs inside its own tab, one tab for each sheet, and each sheet has its own tick box, "Import this sheet as a table" (buttons beside the row tick or untick every sheet). Visible sheets start ticked. Hidden and very hidden sheets are listed with a note, and are not ticked. A sheet with no values, a sheet of more than 2,000 columns and a sheet with a cell beyond Excel's last row or column are listed and cannot be ticked, each with its reason; chart sheets are not listed. A ticked sheet has what a CSV file's tab has: the table's name, a tick box "The sheet has a row of column names" with "Column names are on row", and the row of names with the first rows as they will be read, and it says how many rows and columns its values span and, when they do not start at A1, where. A workbook that is large asks first, in its own tab: "Read this file" or "Leave this file out". When the import ends, the report has two notes more: how many formula cells of a sheet came out empty, and, for a column whose number format showed zeros that the table does not hold, an example (Excel showed `00123` for the number 123). The evidence file lists each table with the sheet it came from.
  - What is in a table: the cells are read by what they hold, not by how they look, and nothing is cleaned. A date is ISO text (`2023-08-05`, with ` 14:30:00` after it when it has a time of day), a time of less than a day is `HH:MM:SS` and a duration (a format with square brackets, `[h]:mm:ss`) is `H:MM:SS`, hours free to pass 24. A number is the number the cell stores: a cell that shows `£1,234.50` holds 1234.5, and a cell that shows `00123` holds 123. A date-formatted number that no date can be (negative, or past the year 9999) is imported as that number. A formula gives the last value the workbook stored for it, and a formula with no stored value is a blank. True and false are the words `TRUE` and `FALSE`, an error cell such as `#N/A` is its text, hidden rows and columns are imported, and of a merged block only the top-left cell holds its value. The table is the smallest rectangle that holds every value, so a value left by accident far below the data makes the table that long in blank rows.
  - Limits, to weigh before switching `excel-import` on for students:
    - How a workbook is read: a workbook is read whole into memory by one call of the library that cannot be interrupted, so the page does not respond while it is read (no progress, no Cancel, and the browser may say the page is not responding), and the tab needs many times the file's size.
    - What it costs, measured: in real Chromium (158) and Firefox (159) on one fast desktop (a Ryzen 7 9800X3D with 30 GB of memory, the browser allowed 9 GB), with workbooks of one sheet of 20 columns made for the purpose: an `.xlsx` of just under 100 MB of sheet data, which is read without a question, froze the page for 2.8 to 5.2 seconds and took 0.7 to 2.0 GB; just under 300 MB, 8.5 to 15.6 seconds and 1.6 to 4.5 GB; just under 500 MB, 15.9 to 26.2 seconds and 2.5 to 5.1 GB. An `.xls` of just under 20, 50 and 100 MB froze it for 0.9 to 1.3, 2.2 to 3.3 and 3.0 to 9.3 seconds, with 0.6 to 0.8, 1.3 to 1.6 and 2.2 to 3.8 GB. These are the figures of that machine: a lab PC is slower, perhaps two to three times, and may have far less memory, and none has been timed.
    - Firefox: it cannot read a workbook of many texts (or half texts, half numbers) whose sheets unpack to just under 500 MB: it runs out of memory at about 7 GB, and the student is told "The browser ran out of memory while reading this workbook, so it was not read. ..." (Chromium read the same workbooks with 3.8 to 5.1 GB; under 300 MB of sheet data both browsers read everything that was tried).
    - What is not guarded when a browser runs out of memory: the import itself after a reading that just fitted (the page then stays busy until it is loaded again), the small steps before the library's call, a browser that never has room again, and a tab that crashes outright.
    - The limits as built, and a workbook with a sheet missing: a large workbook that the library comes back from with one sheet missing is refused in words that name both causes, the size as the likely one and damage as the other, because the library gives up on a sheet without a word in both cases. The limits are the plan's, for each file: an `.xlsx` is measured by what its sheets unpack to, not by its size, so it asks first over 100 MB of sheet data (the question adds a warning about memory over 300 MB) and is refused over 500 MB, or when all its parts unpack to more than 1 GB (a picture in it does not count towards the first two, but takes memory as large as itself); an `.xls`, a web page, an XML spreadsheet and a zip whose directory cannot be read are measured by their size, asking over 20 MB (a warning over 50 MB) and refused over 100 MB. Several large workbooks chosen together are all held while the dialog is open.
    - A damaged `.xls` can freeze the page for good: the format has no checksums, a changed bit can send the library into a loop that never ends, and only a worker that the page could end would guard against it, which the plan's section 10 settles to do without (the owner can weigh that again). An `.xlsx` is not exposed in that way: the zip's own checksums are checked before the library sees the file, and of every copy of one workbook with a single bit changed, none hung the library.
    - What the owner is asked to weigh again: the plan's section 7 puts a stricter set to the owner, to refuse an `.xlsx` over 300 MB of sheet data (Firefox could not read one of just under 500 MB that holds many texts, and read those of just under 300 MB; nothing between was tried), and says that an `.xlsx` is measured by what its sheets unpack to, which is a change to the plan's sentence about size. A small file can still cost the page a great deal: a few kilobytes of crafted XML (a hyperlink on a range of millions of cells, one very long text, thousands of sheets, tens of thousands of merged blocks) or a web page with a colspan on every row make the page freeze for seconds or minutes and take gigabytes, and the zip check can be got round by a file that is made to do it. The limits do not bound that, only a worker the page could end would; nothing here is guarded, and the owner decides whether to guard the likeliest of them (the section on limits in `CODEMAP.md` lists them with their figures).
    - As for `import`, an imported database is lost on a reload until the plan's Phase 4 is built.
  - Not yet looked at by hand, and to be before `excel-import` is switched on for students: the time and the memory of a workbook of 20 MB and of 100 MB on a lab PC, Safari (in which the site has never been tested), one real course workbook of each kind with the import report read as a student would read it, the dialog and the report in light and dark (the plan asks for the screenshots to be sent to the owner), the dialog read by a screen reader (NVDA or VoiceOver) and in Windows' high contrast mode (tried only as roles, names and an emulation of forced colours). The plan's section 9 lists them.

## Run it locally

Serve the repository root with any static file server: from the repository root, `python3 -m http.server 8000 --bind 127.0.0.1` or `make serve` (`make serve PORT=9000` for another port). Then open http://localhost:8000/ (or your port). Do not open the address that `make serve` and a plain `python3 -m http.server` print, such as `http://0.0.0.0:8000/`: browsers do not treat it as a secure address, so the evidence export and `verify.html` cannot compute their checksum there. Opening `index.html` from the disk does not work either: the page loads ES modules and fetches the datasets. The app's page runs `bundle/app.js` and `bundle/app.css`, built from `js/` and `css/`, rather than those files themselves (all but its three small classic scripts): after editing them, run `npm run build:app` and reload ([The app bundle](#the-app-bundle), below). Anything else (a dataset, an exercise set, About) needs no build: edit it and reload.

`CODEMAP.md` is a map of the code: what each module does, how a database opens and a query runs, what is stored where, and how to extend it. Read it before changing code.

## Tests

The tests need Node and Playwright (development tools only; the site itself needs no build). The first time:

```
npm ci
npx playwright install chromium firefox
```

Then:

```
npm test
```

`npm test` runs Chromium and Firefox, each against the site at the server root and mounted at `/repo/` (as GitHub Pages serves a project site), and is some 16,000 tests (`npx playwright test --list` counts them), so it takes a long while: run the files of what you changed as you go, and the whole of it before you push. It starts its own static servers on ports 4173 and 4174; if those are busy, set `TEST_PORT_BASE` (it and the next port are used). To run one file or one browser: `npx playwright test tests/m5-results.spec.js --project=chromium-root`. `PW_WEBKIT=1 npm test` adds WebKit (after `npx playwright install webkit`; it needs system libraries that not every machine has).

## The editor bundle

The editor is [CodeMirror 6](https://codemirror.net/), bundled with esbuild into `vendor/editor.js` (about 390 KB, 130 KB compressed; the plan's budget is 500 KB), with the licences of the bundled packages in `vendor/codemirror.LICENSE.txt`. The bundle holds the library only: what SQL Lab does with it (the keys, the suggestions, the look) is `js/lab/code-editor.js` and `css/editor.css`, which go into the app bundle (`npm run build:app`, [below](#the-app-bundle)), not into this one. To change a CodeMirror version, set it in `package.json` (exact versions; `@lezer/common` and `@lezer/lr` are pinned under `overrides`), then:

```
npm install
npm run build:editor
```

and commit `vendor/editor.js` and `vendor/codemirror.LICENSE.txt`. A test (`tests/ui3-editor.spec.js`) fails while the committed bundle differs from a fresh build (`node tools/build-editor.mjs --check`).

## The app bundle

The app's page, `index.html`, loads its modules and its stylesheets as two files: `bundle/app.js`, the modules of `js/` it runs, bundled by esbuild (not minified, so the names stay readable; about 454 KB, 119 KB compressed), and `bundle/app.css`, its stylesheets of `css/` joined in the order of the cascade (about 109 KB, 23 KB compressed). A first visit then asks for 18 files (20 in Firefox, which fetches two icons at once) rather than 85 (87): 14 that every visit needs, the list of exercise sets, and one file for each of the three sets. That is for a class: students opening the site at the same moment from one school network are one burst of requests from one address, and GitHub Pages answers a large burst with "429 Rate limit exceeded" for minutes, while the page loads half its files. CodeMirror stays a file of its own (`vendor/editor.js`), so the plain editor still takes over when it cannot load. About and the evidence check page load their few files from `js/` and `css/` directly.

`js/` and `css/` stay the source; never edit `bundle/` by hand. After changing them:

```
npm ci              (once)
npm run build:app
```

and commit `bundle/` with the change. A test (`tests/app-bundle.spec.js`) fails while the committed files differ from a fresh build (`node tools/build-app.mjs --check`). The deploy does not run that test or build anything: it publishes `bundle/` as committed, so a change to a module of `js/` or a stylesheet of `css/` that the app's page bundles never reaches it unless the rebuilt `bundle/` goes with it. (The page's three classic scripts, `js/lab/theme-boot.js`, `storage-guard.js` and `engine-guard.js`, and the files of About and the evidence check page are loaded from `js/` and `css/` directly, so a change to them goes out as it is.) Run the tests, or at least `node tools/build-app.mjs --check`, before you push. A new stylesheet for the app's page goes in the list in `tools/build-app.mjs`: the build fails on a stylesheet that no page uses. In a test, reach a module of the app's page through the bundle, `const { checker } = await import("./bundle/app.js")`, which gives the very instance the page runs; the bundle exports the modules listed in `EXPOSE` in `tools/build-app.mjs`.
