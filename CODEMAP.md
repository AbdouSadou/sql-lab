# CODEMAP

Map of the code as it stands. Written for engineers and agents who extend it; update it in the same change as the code. The requirements are in `SQL Playground Build Spec.md`, which is kept next to the working copy on purpose and is not part of the repository (so it is not deployed either); `README.md` is for the instructor, the marker and a developer picking the repository up.

The site is a static, browser-only SQL playground based on SQLime (nalgeon/sqlime): SQLite runs as WebAssembly, there is no build step, and the repository root is the site. Upstream's execution core is kept; everything added lives in `js/lab/` (and `css/`), and `js/index.js`, which is rewritten (see below), reaches it through the named seams of section 2.

**What differs from upstream.** `js/sqlite/` differs from upstream only by the removed gist code and the one `runSql` call in `fromSql` (`manager.js`); nothing else in it was touched. `js/index.js` is substantially rewritten, not lightly modified: 640 lines added and 216 removed against upstream's file (`git diff --numstat main -- js/index.js`, working tree). Its `execute()` goes through `runSql` (`js/lab/runner.js`) instead of `SQLite.execute`, its load flow (load tickets, `openCurrentUrl`, `startFromDataset`; the demo database and gist saving are gone) is new, it carries the seams of section 2, it wires the app shell of the UI plan's Phase 2 (top bar, sidebar tabs, menus, pane sizes, status bar), and since Phase 4 it drives the results pane through a load (its loading state, a failure that keeps the view) and lets a run wait one frame (4.2). Merging upstream changes to it will conflict and has to be done by hand. Other upstream JavaScript files changed too (added/removed lines): `js/components/sqlime-editor.js` 222/11 (it draws CodeMirror inside itself since the UI plan's Phase 3, section 4.5); `js/db-path.js` 28/15; `js/storage.js` 33/3; `js/printer.js` 14/8 (upstream's printer with escaping added (`escapeHtml`) and BLOB cells shown as `x'<hex>'`, section 8). Upstream's `<command-bar>`, `<tool-bar>`, `<db-name>` and `<copy-on-click>` components (`js/components/command-bar.js`, `toolbar.js`, `db-name.js`, `copy-link.js`) are deleted: the app shell replaced them. The UI plan's Phase 4 deleted `<sqlime-status>` (`sqlime-status.js`, with `css/status.css`) and `action-button.js` too: the results pane (`js/lab/results.js`) and the toasts (`js/lab/toast.js`) replaced the status line, and the empty-database welcome's About button is a plain link. `js/components/` keeps `sqlime-editor.js` and `sqlime-result.js`. `js/controllers/` is untouched. Outside `js/`, upstream's `index.html` (rewritten for the shell: 228 lines added and 47 removed, `git diff --numstat main -- index.html`), `about.html`, `README.md`, `Makefile`, `.gitignore`, most of `css/` and the icons in `img/` are changed as well, so merging those can conflict too. Removed from upstream: `js/github.js`, `js/settings.js`, `js/sqlite/dumper.js` and the gist code in `js/sqlite/`, `css/layout.css`, `header.css`, `toolbar.css` and `commandbar.css`, its test page, its deploy workflow, `CNAME`, the demo files, `settings.html` and `img/cover.png`.

References are `file` plus function name, since line numbers drift. The Playwright tests in `tests/` pin most behaviour described here (section 11); a statement with a test name after it is checked there.

## 2. Start-up and the page controller

`index.html` runs, in order: the classic `js/lab/theme-boot.js` (first in `<head>`, on every page: it puts the stored theme on `<html>` before the first paint), the head module `js/lab/brand.js` (writes `APP_NAME` into the title and every `[data-app-name]`); then, at the end of `<body>`, the **classic** scripts `js/lab/storage-guard.js`, `js/lab/engine-guard.js`, `vendor/sqlite3.js` (defines `sqlite3InitModule`, does not start the engine) and `vendor/lz-string.min.js`; then the modules `components/sqlime-editor.js` and `sqlime-result.js` (each defines its element, which upgrades; the rest of the page is static markup; the editor element starts loading `vendor/editor.js` at once, which a `<link rel="modulepreload">` in the `<head>` has already asked for, section 4.5); and last `js/index.js`, which builds the `ui` handles (`buttons.{reset, execute}`, `topbar`, `toolbar` = `#editor-toolbar`, `fileInput` = `#open-file-input`, `editor`, `status` = `#status` (the summary line's text), `summary` = `#results-summary`, `pane` = `#results-pane`, `result`) and the `actions` (`executeCurrent`, `copyLink`, `exportDatabase`) / `shortcuts` (`o`, `u`) maps, exposes `window.app = {actions, ui, get database, whenIdle()}` (`whenIdle()` resolves once no run is waiting or running: a Run starts one frame after it is asked for, section 4.2; tests wait on it), mounts the lab modules, registers listeners and ends with `startFromCurrentUrl()`. Order dependencies: `index.js` uses `ui.editor` at once, so the element modules must have run (module order); a mount that needs another's result comes after it (`mountRunLog` before `mountEvidence`, `mountResults` and `mountEvidence` before `mountExportMenu`); `mountExercises` comes before `mountResults` but calls it only later, through `showIdle` and `modeChanged`; and `mountTabs` calls its `onShow` once while mounting, before `runLog` exists, which is why `index.js` reads `runLog?.refresh()`.

`js/index.js` holds the current database (`let database`, module-private) and owns load, execute, rename (from the export dialog) and rendering of the status. It reaches `js/lab/` only at these seams:

**Page events.** Lab modules follow the page through two events dispatched on `document` by `announce()` in `index.js` (documented in the comment above it). They are the only coupling between the controller and the features; do not monkeypatch upstream objects.

- `lab:database-loaded` `detail {database, dataset, exercise}`: a database is open (page load, the switcher, upload, open-from-URL, the empty fallback). `dataset` is the manifest entry or null; `exercise` is `{set, exerciseId}` when a set opened with it, else null (the exercise panel opens or closes on it).
- `lab:run-finished` `detail {database, sql, ok, rows, error, elapsed, resultSet, changes, preview}`: after every run that had SQL, failed ones too (statements before the error stay applied). `rows` is the full row count (not the 500 shown; 0 for a run with no result set), `error` the engine's message alone on one line (`errorText`), `elapsed` the run's time in ms, `resultSet` false when no statement returned a result set (the status bar then has the summary line's words: "Done in 2 ms", or "Done. 3 rows changed in 2 ms"), `changes` the rows the run changed for such a run (null otherwise, or when it ran no INSERT, UPDATE or DELETE; section 4.2) (those three for successful runs only). `preview` is always false since the UI plan's Phase 4, which removed the table preview the app used to run on open; loggers still skip a run with `preview` true. An empty Run is not announced.

Custom events of the elements, for completeness: `ui.editor` fires `execute` (detail = SQL; does not bubble) and `start` (first input; nothing listens to it any more); `ui.fileInput` fires the native `change`, which `index.js` turns into a load (`FileReader`; a `.sql` name is read as text). Neither the elements' old `open-file` and `open-url` events nor the name's `change` exist any more.

## 3. Modules

### 3.1 Upstream code (js/)

| File | Role |
|---|---|
| `db-path.js` | `DatabasePath`: classifies a location as `empty`, `remote` (`http(s)://`), `local` (the browser's URL parser resolves it to this origin), `binary` (an `ArrayBuffer`), `sql` (passed explicitly for a `.sql` upload) or `unsupported` (everything else: `scheme:id`, `//host`, `\\host`, `data:`, `javascript:`, `file:`). `extractName`, `toString` (raw text: escape before showing), `toHash` (unused). |
| `storage.js` | `get`/`set`/`remove` for the last SQL per database name, key `sqlime.query.<name>`. Every access is in try/catch; SQL that could not be written is kept in a module-private `Map` for the page's life. |
| `printer.js` | `{columns, values}` or a table list to an HTML `<table>` string. Escapes every column name, value and table name; a cell is `cellText(value)` first, so a BLOB reads `x'00ff10'` as in the CSV (upstream showed its bytes as `0,255,16`). Since the UI plan's Phase 4 nothing calls it: the result table is built by `js/lab/result-table.js`. `printTables` (a table list whose buttons carry `data-action="showTable"`) has no caller either and nothing handles that action. |
| `sqlite/manager.js` | `init(name, path)` boots the WASM once (`sqlite3InitModule` is single-use; the result is cached in `loading`) and returns an `SQLite` for any path type: remote/local -> `fetchFile` then `fromSql` (name ends `.sql`) or `fromBytes`; binary -> `fromBytes`; sql -> `fromSql`; empty -> `create` (`new sqlite3.oo1.DB()`, `:memory:`). `fromSql` creates an empty database and runs the script with `runSql` (`js/lab/runner.js`), so an uploaded or fetched `.sql` is under the same guard as a Run (section 5); a refused or failing statement throws and `start()` shows "Failed to load database from sql script: ...", and `database.query` is reset to `""` afterwards. `fromBytes` flips header bytes 18/19 from 2 to 1 (no WAL in memory), `sqlite3_deserialize`s into `main` and gathers tables. Exports only `{init}`; the API object is private. |
| `sqlite/db.js` | `SQLite`: `name`, `path`, `capi`, `db` (the `oo1.DB`), `query`, `tables`, `execute` (first result set, object rows; nothing calls it any more, the tables view that used it is gone), `gatherTables`, `getTableInfo` (splices the name raw; unused, do not call), `meaningfulName`. Also `DEFAULT_NAME` (`new.db`), `QUERIES`, `MESSAGES` (`executing`, `invite`, `loading`). |

## 4. Flow: open a database, execute, render

### 4.1 Open

```
startFromCurrentUrl          ticket = beginLoad(); results.showLoading() ("Loading the database"); route = await resolveRoute(window.location)
 -> picker.setManifest(route.manifest)       (the switcher's list, set before the stale check: the list is true whichever load wins)
 -> the loading state is named (the dataset's manifest name, else the file name)
 -> route.dataset?  fetchDataset(dataset, {onProgress}) (relative URL, bytes validated, counted into the progress bar)
      fails, a database open (back/forward step) -> kept, results.loadFailed: the view from before the load back, the band "The previous database is still open" above it, switcher synced
      fails, none open (first load)              -> dataset = null, problem = "could not be loaded, so an empty database is open", empty database
      ok -> path = DatabasePath(copy of the bytes, "binary"), name = file basename; the fetched buffer is kept for keepPristine
 -> else DatabasePath(route.database)         a plain fragment path, or "" (empty database)
 -> start(name, path, {sql, dataset, pristine, ticket, exercise})
      unsupported path -> no loader call, "Failed to load database from <address>" (results.loadFailed: over the view kept, or the band alone)
      manager.init(name, path), then the stale check (ticket !== latestLoad: close the new database, show nothing)
      database = loaded, the previous connection is closed; pristine bytes kept (dataset) or cleared (anything else); openDataset = dataset
      setShareContext({dataset: dataset?.id})
      database.query = exercise ? lab.editorSql(exercise, sql) : sql ?? (database.query || storage.get(database.name))
      title, editor value, focus the editor (unless keepFocus), announce("lab:database-loaded") (the switcher, the schema, the status bar, the run log and the exercise panel follow that event)
 -> a dataset the engine cannot open, none open yet -> start() again on an empty database with the "could not be loaded" message
 -> showStarted({shared, notice, problem})
      results.showEmpty({variant, notice, problem}): "no result yet", nothing run (section 8)
        variant "shared" (the editor holds a link's SQL), "restored" (SQL from storage, or an exercise's draft) or "fresh" (an empty editor)
        problem (a damaged link, a manifest or dataset problem): the error band above it
      a load the student asked for (anything after the page's first) -> the toast "Opened <name>"
```

Other ways in:

- `startFromDataset(dataset, exercise)` (the database switcher, and the set picker when the set's dataset is not open): ticket, the loading state with the dataset's name, `fetchDataset` with its progress, `start(..., {keepFocus: true})`, then `history.pushState` of `?db=<id>` (or `?set=<id>` with an exercise; relative, no fragment). On failure the previous database stays open, `picker.sync()` puts the switcher's label back, and `results.loadFailed` brings back what the pane showed before the pick with the band above it. Focus is not moved to the editor on purpose: a menu returns it to its button, so a keyboard user can keep choosing.
- `openSet(set)` in `set-actions.js` (the Exercises tab's set menu): when the open database is the set's dataset (`getPristineId() === set.dataset`, nothing loading) it is kept, because reloading would discard the student's work (`lab.open(set)`, `pushState("?set=<id>")`); otherwise `startFromDataset` with the exercise. `closeSet()` cancels a load still on its way, `lab.close()`, `pushState("?db=<id>")` (or `./` for a non-dataset database); a cancelled load leaves "Loading database..." behind, so the invitation replaces it.
- `startFromUrl` ("Open from URL…" in the switcher / Ctrl+U: the dialog of `open-url-dialog.js`, which refuses an empty or unsupported address inline; the loading state names the file, with no size; pushes `#<url>`), `startFromFile` ("Open a file…" / Ctrl+O: `FileReader`, `.sql` as text, else an `ArrayBuffer`; the loading state names the file with its size, already all read; pushes `./`), and `popstate` (back/forward, hash edits, a pasted link in an open tab), which goes through `startFromCurrentUrl`. The fragment stays in the address bar after opening a link and `?db=` after a pick, so a reload restores the same state.

**Stale-load guard.** Every way of opening a database takes a ticket from `beginLoad()` (`++latestLoad`, `loading = true`) before any fetch and passes it to `start`; a load whose ticket is old after an `await` (after `resolveRoute`, after the dataset fetch, after `manager.init`, and in `start`'s `catch`) is dropped without touching the page, and its failure is silent. The last request always wins. `endLoad(ticket, opened)` runs in a `finally`, only the latest counts: it clears `loading` and, when nothing opened, syncs the switcher and the set picker (they show what is open again). While `loading` is true `execute` refuses (`LOADING_BUSY_MESSAGE`, nothing run or saved).

**Behaviours worth knowing.**

- **Nothing runs on load.** Restored SQL (storage, a share link, a draft, a history entry) is put in the editor and never run; only an explicit Run or Check executes SQL. A runaway query saved earlier, or sent in a link, must not hang the tab on load. Anything new that restores SQL keeps this rule. Since the UI plan's Phase 4 the app does not run the first table's preview on open either (inventory row 82): a first visit has an empty editor and "no result yet" with the sample queries, and the preview's query is the fallback sample for a database without manifest samples. `app.openEmpty()` gives an empty start.
- A failed load shows the error band `Failed to load database from <path>` (plus `: <exception>`; `loadFailedMessage`), as text. `database` is assigned only after a successful load, so a failure leaves what was open, and the results pane shows what it showed before the load (the student's result is still true of it) with the band above it (`loadFailed`, section 8). With none open, Run shows the band "No database is loaded." (`NO_DATABASE_MESSAGE`) and "Database (.db)…" a toast with it, instead of throwing.
- With no usable manifest or dataset the app opens an empty in-memory `new.db` with a specific message; upload and open-from-URL work; the next start retries the manifest.
- Choosing the same file twice loads it twice (`index.js` clears the file input after reading).
- The logo links to `./` (a full navigation: the default dataset).

### 4.2 Execute

```
Ctrl/Cmd+Enter in the editor -> CustomEvent "execute" {detail: editor.query} -> execute(detail).catch(ignoreRejection)
Run button -> ActionController -> actions.executeCurrent -> execute(ui.editor.query)

execute(sql, {quiet})                              index.js
   loading -> a note toast (LOADING_BUSY_MESSAGE), refused; no database -> the band "No database is loaded."
   sql = sql.trim(); storage.set(database.name, sql)              (saves what was run, i.e. the selection if any)
   empty -> "no result yet", its heading said, return (no lab:run-finished)
   run = database; endRun = results.startRun()     ("Running…" armed, invisible for 300 ms); pendingRuns++
   await afterPaint()                              one frame drawn (rAF, then a task; at most 250 ms in a tab that draws none)
   database replaced meanwhile, or a load begun -> dropped (rejected with RUN_DROPPED, {dropped: true}; nothing run, shown or announced; a Check whose run was dropped checks nothing)
   before = run.db.changes(true)                   (sqlite3_total_changes)
   result = runSql(run, sql)                       js/lab/runner.js
   changes = result ? null : changedRows(run, before, sql)
   showResult(result, elapsed, {changes, quiet})   -> results.showResult (quiet: shown, not said: a Check's run)
   catch -> showError(exc) -> results.showError; returns a rejected promise
   finally -> announce("lab:run-finished", {database, sql, preview: false, ok, rows, elapsed, resultSet, changes | error}); endRun(); pendingRuns--
```

- **Run answers at once.** `executeCurrent` (the Run button's action) starts `execute` and returns a resolved promise: `ActionController` holds a button disabled until its action's promise settles, and a disabled button loses the keyboard focus, so a Run that waited its frame took the focus off Run (to `<body>`) after every press. Run is never disabled during a run now (the page is blocked during it anyway); two quick presses run twice, as they always did.
- **The frame before a run.** A run blocks the page until it ends (the engine is synchronous on the main thread; a Web Worker is held back by the plan), so "Running…" after 300 ms (the plan's section 5) can only be drawn by the compositor: `results.startRun()` puts the overlay in the page with a CSS animation that waits 300 ms and fades it in, and `execute` lets one frame be drawn (`afterPaint`) before `runSql`, so the animation is already on the compositor when the run starts. A run that ends sooner removes it before it ever shows. Without the frame nothing appears during the run (checked by recording a 1.5 s run in Chromium and Firefox; `tests/ui4-results.spec.js` checks the order: overlay, a frame, then the run). The frame costs every run about 16 ms and makes `execute` finish after the key press or click that asked for it: `window.app.whenIdle()` resolves once no run is waiting or running, and the test helpers (`app.run`, `app.settle`) wait on it. Check (`runCheck`) awaits `execute` as before.
- **Rows changed.** For a run with no result set, `changes` is the growth of `sqlite3_total_changes` over the run (every row an INSERT, UPDATE or DELETE touched, triggers and cascades included, summed over its statements); when it did not grow, 0 if a statement of the run begins (after comments) with INSERT, UPDATE, DELETE or REPLACE (an UPDATE that matched nothing: "Done. 0 rows changed"), else null ("Done" alone: CREATE TABLE and the like). A DML statement inside a CTE (`WITH ... INSERT`) that changes nothing reads as "Done". Reading the counter changes nothing about the run.

- `ui.editor.query` is the selected text if the whole selection lies inside the editor, else the full text (so text selected in a prompt or a result cell is never what Run executes).
- A multi-statement run shows **the last statement that has result columns** (zero rows included): `select 1 as a; select 2 as b, 3 as c` shows `b, c`; trailing DDL/DML does not replace it; a final `select ... where 0` shows "0 rows". **Duplicate column names are kept** and the order is the SELECT's. The status line and table are one per run, not per statement; time covers the whole run.
- Statements before a failing one stay applied: nothing wraps a run in a transaction (no `BEGIN` in `js/`), so each auto-commits; the failing one and the rest never run. The failed run's rows are lost (the error path clears the table).
- `execute` returns a rejected promise on error (and when it refuses or drops a run); the editor listener swallows it (`ignoreRejection`), `ActionController` swallows it for buttons, and `runCheck` catches it.
- The editor keeps Tab for indentation (two spaces); Escape then Tab / Shift+Tab leaves it (Help says so, and `#editor-hint`, a visually hidden sentence, is the editor's `aria-describedby`); any other key or a blur cancels the Escape. Section 4.5 has the rest of the editor's keys.
- Fidelity: Copy link carries `ui.editor.value`. In CodeMirror that is the text exactly as typed. In the plain box it is `innerText`: in Chromium typed text makes `<div>` lines, so a blank line reads back with one extra newline (two Enters give three newlines; it matters only for a string literal or comment that spans a blank line); the recipient sees exactly what the sender's `value` read (upstream behaviour, not changed).

### 4.3 The Schema tab (F4)

`index.js` has one line for it: `mountSchema({container: #schema, editor: ui.editor})`. Code: `js/lab/schema.js`, `js/lab/insert.js`, `css/schema.css`.

- **Where.** `#schema` is the content of `#panel-schema`, the first tab panel of `nav#sidebar` (4.4), which scrolls on its own. The caret and a selection are carried as offsets into the box's `innerText` (`caretOffsets` counts line breaks as `innerText` does: a `<br>`, and a line block's edges between text). - **Keys.** In a `Prec.highest` keydown handler: `leavesEditor` (Escape arms, the next Tab or Shift+Tab is left to the browser; CodeMirror's own two-second Escape mode is reset on blur, and both are cancelled by a press in the editor, so an Escape never outlives the visit or outlasts the student going on editing) and Ctrl or Cmd with Enter, any other modifier included (as the box), fires `execute` and closes the completion list. Then `defaultKeymap` without its Escape binding (`simplifySelection` would collapse the selection, and Escape is the first key of the way out to Run, which runs the selection; Ctrl/Cmd+/ toggles `-- ` comments; its Ctrl/Cmd+Enter `insertBlankLine` never runs) and `historyKeymap` (Ctrl/Cmd+Z, Ctrl+Y, Ctrl/Cmd+Shift+Z) without its Mod-U (`undoSelection`, "undo the last change or selection") and Alt-U pair: Ctrl/Cmd+U is the page's "Open from URL…", and with the binding the key also undid the student's last edit (found in Phase 4; `tests/ui4-review.spec.js`). Ctrl/Cmd+Shift+Enter with a set open is taken before CodeMirror by `exercise-panel.js` (capture phase on the document), and Ctrl/Cmd+O and U still reach `ShortcutController`.
- **Completion.** `autocompletion({override: [lang-sql's schemaCompletionSource, the columns, the words], icons: false, selectOnOpen: false, filterStrict: true})`. The schema source completes tables and views ("table" / "view") and, after `name.` or an alias and a dot, that object's columns with their types; the columns source offers every column for a word typed on its own (detail: the tables that have it, boost -1); the words are SQLite's keywords and types (capitals, boost -1) and functions ("function"); none of them inside a string, a quoted name or a comment (`ifNotIn`). A name that needs quoting is inserted as `identifierForSql` writes it, as the Schema tab does. Nothing is picked when the list opens, so Enter is a new line until the student picks a name with the arrow keys (a line ending in an alias, `FROM orders o`, would otherwise get the first name); a name already typed in full is not offered (`withoutTyped`, which filters again at once through the result's `update` as the word grows: a list waiting for a fresh answer ignores the arrow keys). lang-sql reads a name only from an ASCII letter or digit on, so its answers are dropped where it did not read what was typed (`readSoundly`): the end of a longer word (the `pr` of `__pr`, the `b` of `üb`: it would splice a name onto the rest), the columns after a name it cannot read and a dot (`café.`, `_a.`, `"a""b".`: it offers the tables), and a quote typed right after a closing quote (a quote doubled inside a name, which it takes for a new name). The editor's own sources answer instead: names that start with `_` or a letter outside ASCII are offered with the columns, and after such a name and a dot the qualified source offers that table's columns (an alias of such a table is not followed). Words are matched whole, letters of any script with their marks; no keyword or function is offered after a dot. After an opening quote lang-sql quotes the name itself without doubling a quote inside it, so `quotedRight` doubles it. The namespace has no prototype, so a table named `__proto__` is a name like any other. When the list opens CodeMirror's live region says how many names it holds and how to pick one (`completionsOpenedText`), since nothing is picked to announce; once per opening (a list that waits for a fresh answer while it is open has not opened again). `editor-schema.js` hands the names over on `lab:database-loaded` and after a run that moved `PRAGMA schema_version`; the plain box keeps them for a late CodeMirror.
- **Look.** The dialect is lang-sql's SQLite with SQLite's own keyword list and its functions as the built-ins (lang-sql's SQLite built-ins are the sqlite3 shell's dot commands, which would draw a column named `mode` as a function); case-insensitive names, double quotes first. `tagHighlighter` gives classes, not inline styles: `sql-keyword` (keywords, types, `NULL`, `TRUE`; 600), `sql-function`, `sql-string`, `sql-number`, `sql-comment` (italic), and `sql-quoted-name` for a `"quoted"` name, which stays ink (a name, not text), coloured by the `--syntax-*` tokens in `css/editor.css`, where every CodeMirror part is styled under `#editor` (CodeMirror adds its base theme to the page later, with selectors of up to five classes): 48 px of line numbers in graphite, 12 px from the SQL; 14 px code face at 1.6; the caret's line and its number on `--sunken` only while the editor has the focus (`:focus-within`, which changes with the focus itself; CodeMirror's `cm-focused` class follows a moment later), and the line not while text is selected (`sql-selecting` on `.cm-editor`, from `editorAttributes`: CodeMirror draws the selection under the text, so an opaque tint would hide it); selection and the matched bracket on `--accent-subtle` (in forced colours both the selection and the picked name are outlined in `Highlight`); the caret does not blink under `prefers-reduced-motion`; the focus ring drawn by `.cm-editor:focus-within::after` over the editor (an outline would be under the line numbers, which stay put while the SQL scrolls sideways); the completion list styled as a menu (4 px inside the list, 32 px rounded rows, 44 on a touch screen). Lines do not wrap (the mockup draws the editor with `white-space: pre` and `overflow-x: auto`): a long line scrolls sideways inside the editor, never the page, and the plain box still wraps as it always did.
- **Paste and drop.** CodeMirror pastes `text/plain` only and drops text at the drop point; a drop carrying files is cancelled and inserts nothing (`code-editor.js`), as in the box. A drag that starts in the editor is CodeMirror's move until its `dragend`; as in the box (`plain-text.js`), a pointer or key event that comes first means the drag ended without one, and `code-editor.js` then sends CodeMirror a `dragend`, so the next drop from elsewhere is not taken for that move (which would delete the dragged text).
- **The bundle.** `tools/editor-entry.js` re-exports the CodeMirror pieces used; `tools/build-editor.mjs` bundles it with esbuild (ESM, minified, the README's browser floor as target, a banner naming every package and version), checks that the packages bundled are exactly the fourteen it lists, writes `vendor/codemirror.LICENSE.txt`, and fails over 500,000 bytes. `--check` builds in memory and fails if the committed files differ (`tests/ui3-editor.spec.js` runs it). Versions are exact in `package.json`, and `@lezer/common` and `@lezer/lr` are pinned under `overrides` (each was chosen at least two weeks old).

## 5. Running SQL: `js/lab/runner.js`

- `splitStatements(capi, sql)`: cuts at each `;` where `sqlite3_complete` says the text since the last cut is whole, so a semicolon inside a string, comment or trigger body does not split and a long script is never rescanned. A `;` inside a string, a quoted or bracketed name or a comment is not even asked about: `nextSemicolon` (private) steps over those with `indexOf`, by `sqlite3_complete`'s own rules (a quote runs to the next one of its kind, `[` to `]`, `--` to the next LF only, and `*/` is searched from right after the `/*`, so `/*/` stays open; anything unclosed means no more semicolons), because asking costs a pass over the statement so far and a text value with 100,000 semicolons (a `.sql` upload goes through `runSql`) took seconds or threw. `sqlite3_complete` remains the only judge of whether a `;` ends a statement, which is what keeps trigger bodies whole (`m4-runner.spec.js` counts its calls, and a one-off differential run of 150,000 random strings against the previous splitter showed no difference). Statements are trimmed; a lone `;` is dropped, and so is text that is only whitespace, comments and semicolons (a `-- note` after the last statement is not a statement; a comment in front of a statement stays part of it, and `stripLeadingNoise` removes it where the statement is quoted back to the student). An unterminated block comment needs at least one character after its `/*` to count as a comment, and whitespace counts, as in SQLite: `/*` followed by any character is a comment, a bare `/*` as the very last two characters is a slash and a star. So `select 1; /*` keeps `/*` as a statement and the engine's `near "/": syntax error` shows, while `select 1;\n/*\n` and `select 1 /* ` run (`addStatement` trims, but keeps the one blank character after a final `/*`, both for the nothing-to-run decision and for the text executed: `select 1 /* ` is executed as written). `/* a` is a comment in both. Checked against `python3`'s `sqlite3` module (SQLite 3.54, `executescript`) on 244,268 strings built from `select 1`, `;`, blanks, `/*`, `*/`, `*`, `/`, `--`, `x`, tab, `'a'` (up to five pieces) and 177,155 more with CR, a double quote and a trigger: no difference in what runs and what errors (the first set had 1,155 differences before the change). The `sqlite3` shell is no reference: it reads line by line and drops the newline after a final `/*`. One known difference remains, kept on purpose (the lenient side, so text pasted from a page or a document runs as it looks): JS `trim()` also removes Unicode blanks such as U+00A0 at the edges of a statement, which SQLite reports as an unrecognised token. A lone UTF-16 surrogate is replaced by U+FFFD in `runSql` before the text is split (`toWellFormed`): the engine's own conversion swallows the character after it, where `sqlite3_complete` and `nextSemicolon` read U+FFFD, so the statements were cut one way and run another and a `VACUUM INTO` could hide behind a quote the engine did not see (only the authorizer refused it; `m4-runner.spec.js` pins the agreement). Text with a NUL character (U+0000) is refused whole by `runSql` with `SQL_NUL_MESSAGE` before anything runs, because the engine stops reading at a NUL and the statements after it would silently not run. It splits because the engine's `exec` collects rows for the first column-returning statement only.
- `runSql(database, sql)` -> `{columns, values}` of the last statement with result columns, or null. One `database.db.exec({sql, rowMode: "array", columnNames, resultRows})` per statement. Sets `database.query = sql`. Values are numbers, BigInt (beyond the safe range), strings, `Uint8Array` (BLOB) and null. A failing statement throws the engine's exception after `statementText`, `statementPosition` (1-based) and `statementCount` are attached to that same object (class and message unchanged); results.js names the statement from them. They hold student SQL, or the model query when the checker runs it, so the checker drops that exception.
- `engineMessage(exc)`: the engine's text without the `SQLite3Error: SQLITE_...: sqlite3 result code N:` prefix; used for the error band (as it is) and its announcement, the run log, the checker's feedback and `lab:run-finished`.
- **The guard.** The engine's heap limits and its memory filesystem are shared by every connection on the page, and a check opens fresh connections, so student SQL must not leave anything there. `runSql` installs an authorizer (`sqlite3_set_authorizer`, once per connection) that refuses `PRAGMA hard_heap_limit` / `soft_heap_limit` (a low limit survives closing the connection and made every later Check fail) and `ATTACH` of anything but `:memory:` or `''` (a file, or a `file:...?vfs=memdb` URI, would stay in memory for the page's life and be visible to later checks); the student sees "not authorized". `VACUUM INTO` a file reaches the authorizer as an `ATTACH` and would be denied there ("authorization denied"), but `isVacuumInto(statement)` (starts, after whitespace and comments, with VACUUM and says INTO outside comments and quotes, so `VACUUM /* into */` still runs) refuses it first with `VACUUM_INTO_MESSAGE`: the student is told why, and the refusal does not rest on the authorizer alone. The guard applies to every run, Run and Check alike, and to a `.sql` script loaded as a database (`manager.js` `fromSql` calls `runSql`; it used to call `database.execute`, which bypassed the guard), because a file made by a Run would reach a later Check. Temp tables and `ATTACH ':memory:'` die with the connection and stay allowed. Any new way of running student SQL must go through `runSql` or it loses the guard.
- `SQLite.execute` (`db.js`) has no caller left (the tables view that used it is gone) and keeps the old object-row, first-result-set behaviour; do not use it for user SQL.

## 6. Addresses and loading

### 6.1 `resolveRoute(location)` (`router.js`)

Never throws; returns `{database, dataset, sql, exercise, damaged, notice, problem, manifest}`. Priority, first match wins:

1. A share fragment (anything `isShareFragment` accepts; never taken for a database path). If it names an exercise set that loads and whose dataset is in the manifest, that set's dataset opens whatever dataset id the link carries. Otherwise a known dataset id opens it; an unknown or absent id opens the default with a `notice`; the SQL is restored either way (blank SQL counts as none). A damaged link opens the default with `damaged`.
2. A plain fragment (`#datasets/x.db`, `#https://...`): upstream's open-from-URL, `database` set, no dataset.
3. `?set=<id>` with optional `&ex=<id>`: opens the set and its dataset. A set that cannot load, or whose dataset is not in the manifest, adds a notice and routing goes on as if no set was named. An exercise id not in the set adds a notice and selects none. `&ex=` without a set is ignored.
4. `?db=<id>`: a known id opens it, an unknown one opens the default with a notice. An id that does not match `SHARE_ID_PATTERN` is not echoed.
5. The default dataset. If the manifest is unusable and nothing else was asked for, `dataset` is null and `problem` holds the message (empty database).

`exercise` is `{set, exerciseId}` (`exerciseId` null when none was named) or null. Notices are joined with a space. The fragment path is read raw from `location.hash.slice(1)`; there is no `hashchange` listener, `popstate` covers hash edits.

`DatabasePath.inferType` rules: empty -> `empty`; `ArrayBuffer` -> `binary`; `http(s)://` (any case) -> `remote` (a plain `fetch`, so the host must send CORS headers); the URL parser resolves it to this origin -> `local` (`fetch(value)` resolved against the page, so subpath-safe); anything else -> `unsupported` (refused by `start`, no request). The URL parser decides on purpose: a check for `:` or `//` would miss `\\host\x` and `HTTPS://`. Both `local` and `remote` take the `.sql` branch if the whole string ends in `.sql`. `extractName` is the last `/` segment (a query string stays in it); binary, sql, unsupported and empty give `""`, which `SQLite` turns into `new.db`.

Open question for the owner, not changed: a link can carry `#https://some.host/x.db`, which makes the page fetch that host. That is upstream's open-from-URL, kept by the spec, but it lets a crafted link cause one third-party request.

### 6.2 Share links (F3)

Format `#s=<payload>`, `payload = LZString.compressToEncodedURIComponent(JSON.stringify({v:1, d, x, e, q}))` with absent fields omitted (`d` dataset id, `x` exercise set id, `e` exercise id, `q` SQL). The link is the page URL with query and fragment replaced, so it is valid under any subpath and the SQL never reaches a server log. A blank editor omits `q`; an incoming blank `q` counts as none.

Reading is lenient about the start (`SHARE_START`: `#S=`, `#s%3D`, `#?s=`, `# s=`); a fragment that looks like one but does not decode is `damaged`, never a database path, so its payload is neither requested nor printed. `decodeShare` treats the fragment as hostile and returns `{ok:false, reason}` for: `payload` (empty, a character outside the alphabet, a bad `%` escape, over `SHARE_MAX_PAYLOAD_CHARS` = 100,000, or a decompressed JSON over `SHARE_MAX_JSON_CHARS` = 400,000, checked before parsing because lz-string expands a few KB into hundreds of MB), `decompress`, `json`, `shape`, `version` (`v` not 1), `id` (not `SHARE_ID_PATTERN`), `sql` (over `SHARE_MAX_SQL_CHARS` = 200,000). Unknown keys are ignored. Copy link refuses to build a link that would exceed the limit. For an upload, open-from-URL or the empty database the link carries no dataset and the status says so (`NOT_IN_LINK_MESSAGE`).

### 6.3 The dataset manifest (F1)

`datasets/manifest.json`, fetched by the relative URL `MANIFEST_URL` with `cache: "no-cache"`. `validateManifest` accepts it only if: the top level is an object with a non-empty `datasets` list; every entry is an object with a unique `id` matching `SHARE_ID_PATTERN`, a non-blank `name`, and a `file` that is a relative same-origin path (no leading or trailing space, control character, backslash or leading `/`, no scheme, no `..` segment even percent-encoded, and the URL parser resolves it to this origin); `description`, if present, text; `default`, if present, a boolean; and exactly one entry has `default: true`. Otherwise `{ok:false, message}` with the specific reason, shown in the error band; the app starts on an empty database. Unknown keys are ignored. `samples` (the UI plan's sample queries, optional) is a list of `{label, sql}`: an entry that is not two non-blank pieces of text is left out with a `console.warn` for the instructor, and a `samples` that is not a list gives no samples (the first table's rows are offered instead): a teaching aid does not make the manifest invalid. The label is trimmed, the SQL kept as written (line breaks included); the results pane shows the first three (section 8). Northlight's are the first-visit mockup's: "Every product", "Orders per store" and "Revenue share by category" (the mockup's CTE). The `.db` is fetched by its relative `file` and must start with the 16-byte SQLite header, so a server answering a missing file with an HTML page is an ordinary failure. A dataset's database name is the basename of its file, which is also its `sqlime.query.<name>` slot.

## 7. Exercise mode

### 7.1 Sets (`exercises.js`)

- `validateSet(data, expectedId)` -> `{ok, set}` / `{ok:false, message}`. Rules: `id` matches `SHARE_ID_PATTERN` and equals the file name; `title` (the set's too) non-blank; `dataset` an id; `exercises` a non-empty list with unique ids; per exercise `title`, `prompt`, `model_query` non-blank text, `hints` optional list of text (default `[]`), `order_matters` and `check_column_names` optional booleans (default false); unknown keys dropped. Messages are worded for the instructor and echo only ids that matched the pattern.
- `loadSet(id)`: id checked first (no request otherwise), then `fetch("exercises/<id>.json", {cache: "no-cache"})`. Never throws. A success is remembered for the page; a failure is retried.
- **Deploy-time listing (decision).** GitHub Pages cannot list a folder, and adding a set must stay "commit one JSON file", so the app discovers sets by reading the folder page `exercises/`: `listSets()` fetches it (`cache: "no-cache"`) and reads the links with `DOMParser`. `python3 -m http.server` writes such a page itself; the Pages workflow step "List exercise sets" (after staging, before the upload) writes `.site-stage/exercises/index.html`: a minimal page with one `<a href="x.json">x.json</a>` per `*.json` file (names HTML-escaped, and `%` written `%25` in the href because the reader percent-decodes every href, as a real server's listing expects; `nullglob` so an empty folder gives no links, `LC_ALL=C` for a stable order). `tests/static-server.mjs` answers `exercises/` with the same text (`exercisesIndexHtml`) and `m4-listing.spec.js` runs the step's script and compares. Not a manifest: a second list would have to be edited by hand. Only an href whose entire value, percent-decoded, is `<id>.json` is an id (`idsInListing`), and the fetched URL is rebuilt from the id, so a listing cannot send a request off the site. The other plain `.json` file names of the folder (no `/` or `\` once decoded, not matching the id pattern: `Week 3.json`, `week1.v2.json`) come from `badNamesInListing`, cut to 80 characters, and `listSets` makes them `{id: <name>, ok: false, problem}` entries (`SET_BAD_FILE_NAME_MESSAGE`) with no request; that `id` is only a name to show. No listing (404, error, junk) means `[]`; `?set=<id>` and share links do not need one. Entries (ids and unusable names together) are sorted by id, `{id, ok:true, set}` or `{id, ok:false, problem}`, at most `MAX_LISTED_SETS` (the sets first; the unusable names only fill the room the sets leave, so badly named files cannot push working sets out of the menu). The app asks for the folder at every page start without awaiting it.
- **`model_query` is in the loaded set** (the checker needs it, and a student can read it in the fetched JSON; spec section 5 accepts that for formative practice, F9 is the stricter variant and is not built). It must never reach the DOM, an attribute, a message, a URL, the run log or the evidence file by any route: render `title`, `prompt` and `hints` with `textContent`, and never copy exercise objects wholesale into `dataset` attributes or a share link. `m4-panel.spec.js` searches the DOM after loading, failing, passing and every hint for all ten shipped exercises; `m5-evidence-dialog.spec.js` checks the log, the evidence file, the page and storage after a Check.

### 7.2 The checker (`checker.js`)

- Pure parts: `normalizeValue` (INTEGER and TEXT exact, REAL rounded to 6 dp, NULL equals only NULL, BLOB by hex, BigInt exact; an integer-valued number is an integer, so INTEGER 3 equals REAL 3.0; tagged JSON forms `{"$int"}`, `{"$blob"}`, `{"$real": "Infinity" | "-Infinity" | "NaN"}` keep types apart), `normalizeRow`, `serializeRow`, `displayValue`, `compareResults(expected, got, {orderMatters, checkColumnNames})`. `order_matters` false: each normalised row serialised, strings sorted by code unit, arrays compared; true: sequences. Column count is always compared; names (case-insensitive, in order) only with `check_column_names`.
- `createChecker()` -> `{check(set, exercise, sql), clearCache()}`, one per page (made in `mountExercises`). `check` never throws and resolves to:
  - `{status:"pass", rows}`: `rows` is how many rows matched, for the banner's "Correct. 12 rows match." (the UI plan's Phase 5 added it; nothing about what passes changed)
  - `{status:"fail", kind, message, ...}`; kind and spec rule: `sql` (1; `message` = `engineMessage`), `columns` (2; "expected N columns, got M"; a statement list with no result columns is M = 0), `column-name` (3; plus `position`, `expected`, `got`), `rows` (4; "expected N rows, got M"), `row` (5; plus `rowIndex` 1-based, `sorted` true when the index counts rows after sorting, `columns`, `gotColumns`, `expected` and `got`: at most `DIFF_MAX_ROWS` = 3 display-string rows from `rowIndex`; `message` is multi-line plain text and can hold student text).
  - `{status:"unavailable", reason, message}`: `model` (the model query fails or returns no columns: an authoring bug; the generic `CHECK_BROKEN_MESSAGE`, nothing about the query. For the instructor the console gets one warning, `exercise "<set>/<id>" cannot be checked: its model query fails: <engineMessage>` or `... returns no result set`; only the engine's own message with every quoted piece in it replaced by `"…"` (`withoutQuotedText`: SQLite echoes a double-quoted word it cannot find as a column, and a model query can be one), never the query text or the exception's `statementText`; the engine's own step-time warning is cut down to its result code by `engine-guard.js`), `dataset` (the open dataset is not the set's, or no built-in dataset is open: `CHECK_NO_DATASET_MESSAGE`) or `internal` (a connection could not be opened, or anything unexpected; `CHECK_INTERNAL_MESSAGE` says to reload).
- **How it runs.** The pristine bytes are copied (`getPristineBytes()`, two copies taken before any await) and each query gets its own connection through `manager.init(name, new DatabasePath(bytes, "binary"))` (names `model.db`, `check.db`), both closed in `finally`. SQL goes through `runSql` (the guard applies). The model result is cached per `set id/exercise id` (the entry also holds the query and dataset, so an edited file is not served from it); a failure is not cached. The model runs first, so a broken exercise reports `unavailable` even when the student's SQL has an error. Tests count connections by wrapping `manager.init` (it is called as a property).
- **Known limits (decisions).** INTEGER 3 and REAL 3.0 compare equal (friendlier: `AVG` returning 450.0 passes against 450). Two TEXT values that are different invalid UTF-8 sequences compare equal. A result in the right order passes even without an `ORDER BY` the prompt asks for, when the engine happens to emit it so (for example `GROUP BY` on a text key, e08; its hint says ORDER BY is what guarantees it). No timeout exists for a runaway query, in Run or Check.

### 7.3 Progress and saved exercise SQL (`progress.js`)

One localStorage key per set (section 12), holding passes and **per-exercise saved SQL** ("drafts"). Decision: the SQL a student last wrote for each exercise lives in the set's progress record, not in the dataset's free-query slot (`sqlime.query.<name>`), so moving between exercises or reloading never loses work and one exercise's SQL never appears in another. It is saved on every `input` event of the editor, by every Run and Check (the full editor text), and never for text that arrived in a link or was set by the app (those fire no `input`). Opening an exercise shows its saved SQL or nothing; exercise mode never reads the free-query slot (a Run in exercise mode still writes it, because `execute` is shared, so leaving exercise mode can show that SQL as "your last query"). The Reset progress button (`resetSet`) clears passes and saved SQL of that set, not the run log.

`isPassed`, `markPassed`, `passedCount(setId, exerciseIds?)` (pass the set's ids so an exercise removed from the file is not counted), `getDraft`, `saveDraft` (blank removes), `resetSet`. Passing is sticky. Corrupt or foreign stored JSON reads as empty; a storage exception never escapes: that set's progress then lives in memory, and `reportStorage("progress", false)` makes `storage-notice.js` say so. Every write (and `resetSet`) tries `localStorage` first, also for a set that failed before, so when there is room again the set goes back to storage and the notice goes (it stays while any other set is still only in memory). **That first successful write merges what is stored into the set held in memory**, because another tab may have stored passes meanwhile and passing is sticky: the union of passes, and a stored draft only for an exercise this page holds no draft for and did not empty meanwhile (`emptiedDrafts`: a draft the student deleted while the set was in memory is not brought back from the older stored copy; a pass held in memory does come back even if another tab reset the set, because passing is sticky) (without it, memory `{e1}` + `markPassed(e4)` overwrote a stored `{e2, e3}` with `{e1, e4}`). A stored value that could not be read (`getItem` threw) is not written over, also for a set that was not in memory before: `read` marks the empty state it answers with `unread`, and `write` then merges what is stored first, as it does for a set held in memory. If storage still cannot be read the throw puts the set in memory (later writes merge what is stored once it can be read). A set that was read normally is not merged (reads go to storage every time). A `resetSet` whose `removeItem` throws keeps an empty state in memory and reports `reportStorage("progress", false)` like `write`, and notes the set in `pendingResets`: the copy still stored is the one being reset, so the next successful write skips the merge and overwrites it, which completes the reset (a successful `setItem` or `removeItem` clears the mark). Ids that do not match the id pattern are ignored.

## 9. Run log and evidence export (F6, F11)

### 9.1 The run log (`run-log.js`)

- **What is logged.** One entry per Run: `lab:run-finished` with `preview` false. A Check performs its visible run through the same `execute`, so it is logged once; the checker's own runs go through `runSql` and announce nothing, so the model query cannot reach the log. Entry: `{t, sql, rows}` or `{t, sql, error}`; `t` is `utcTimestamp()` (`new Date()`, second precision, so a test controls it with `page.clock.setFixedTime`), `sql` as `execute` ran it (trimmed, never cut), `rows` the full count, `error` the engine's message on one line.
- **The log key.** `logKeyFor(dataset, databaseName)`: the dataset id for a built-in dataset, else `file:<database name>`. It is fixed when the database opens (a `WeakMap` database -> key filled on `lab:database-loaded`), so renaming a database in the export dialog does not split its log. Two uploads with the same file name share a log. `isDatasetKey(key)` (matches `SHARE_ID_PATTERN`, which a `file:` key never does) says whether a share link can exist.
- **Storage.** Key `sqllab.log.<log key>`, value `{v: 1, entries}`, oldest first, at most `RUN_LOG_MAX_ENTRIES` = 200. An append is synchronous: `appendLog` rereads the stored log, adds the entry and calls `setItem` before it returns, and `execute` announces `lab:run-finished` in the same task that shows the result, so a Run that is on screen is already in `localStorage`. A page left at once (a link, a reload, a closed tab) loses nothing; `readLog` reads storage (or the in-memory copy, below) and there is nothing to wait for in a test. **What is promised:** every Run is kept, and two tabs that run at human spacing (tests use tabs 25 ms apart) lose nothing, because each write rereads what the other tab stored. **What is not:** reading and writing one key is not atomic across tabs, so two tabs that append within the same few milliseconds can overwrite each other's entry (a test that ran 90 appends in each of two tabs at once stored 117 of 180 in Chromium); a person cannot run two queries that close. **No Web Lock (decision).** An earlier version queued the entry in a module `Map` and wrote it inside `navigator.locks.request` to close that race. Web Locks are asynchronous, so the entry existed only in memory until the lock was granted and was lost when the page left first: a script that ran a query, waited for the status line and went to `about.html` lost the entry in 180 of 200 runs in Chromium (158 of 200 when it reloaded; Firefox lost none in 200, but the grant is not ours to time). Losing a Run the student can see is worse than the same-millisecond race, so there is no lock, no queue and no asynchronous step in front of the write; tests `a Run followed at once by leaving the page keeps its entry` and the two-tab test in `m5-audit-fixes.spec.js` pin this. Stored text is untrusted: JSON that is not `{v:1, entries:[...]}` is an empty log; an entry that is not `{t: timestamp, sql: non-empty string, exactly one of rows (integer >= 0) or error (non-empty string)}` is skipped. When `setItem` throws the oldest entries are dropped from the *stored* copy one at a time until the new one fits, and the page keeps the whole capped log in a module-private `Map` (also when even the newest entry alone does not fit, or storage is unusable). **The copy in memory is merged, never preferred:** `readLog` and every write combine it with a fresh read of the stored log (`combine` in `run-log.js`): the stored copy is normally a tail of the memory copy and changes nothing, but entries in it that the memory copy lacks were stored by another tab and are added in time order (stable, so one second keeps its order; entries are compared by time, SQL and outcome, as a multiset, so the same SQL twice in a second stays two: mine `[X, X]` with stored `[X, X, X]` is three entries, which the splice in `combine` makes so, test `equal entries are counted one to one when merging`. **Known blind spot, no ids on purpose:** an entry from another tab that equals one of this page's own (same second, same SQL, same outcome) cannot be told from it, so two tabs that ran identical SQL with an identical outcome in the same second count as one entry in this merge path, which is only taken while a log is held in memory after a storage failure). Without this, a tab that had gone to memory mode wrote its stale copy over what another tab stored once there was room again (measured: 6 of 14 entries lost with two tabs). The History tab and the export stay complete while the page is open, and only a reload sees the short stored tail. **A log that cannot be read is not written to:** `stored()` returns `null` when `getItem` throws (an empty array means "nothing stored"); `commit` then keeps the entries in memory and reports failure even if `setItem` would work, because writing the newest entry alone would replace the log with one entry that the page could not read back (measured: 30 Runs on screen, none in the History tab or the export, no notice). **A second limit:** besides 200 entries a log is capped at `RUN_LOG_MAX_BYTES` = 5,000,000 **UTF-8 bytes** of SQL and error text (counted with `TextEncoder`, not `.length`: 200 entries of 24,000 CJK characters are under 5,000,000 characters but 14.4 MB, and with their links 33 MB, against the 20 MiB `verify.html` accepts), oldest entries first (the newest is always kept, whole). Storage has a quota; memory has none, and 200 Runs of 110 KB each made a genuine 21 MB export that `verify.html` refuses (over `EVIDENCE_MAX_BYTES`); links add at most 100,000 characters per entry, so a capped log stays under it. A single entry larger than the limit is still kept whole (and a file with a SQL text over 20 MB would not verify; the editor cannot reasonably hold one). Each commit reports `reportStorage("log", ok)`, where `ok` is true only if the write kept everything **and no other log is still only in memory** (`memory.size === 0`): otherwise a small log that fits would hide the notice while another database's log is still lost on close. `progress.js` reports `"progress"` the same way (no set left in memory), and `storage-notice.js` shows `STORAGE_NOTICE_LOG` / `STORAGE_NOTICE_PROGRESS` in `#storage-notice` (a warning band on `--warning-subtle`, just above the summary line, at the top of the results pane) until every subject has saved properly once more. A page without a document (the Node tests) just skips the event. SQL is never truncated. Nothing throws. Nothing removes a log; the cap drops the oldest.
- **The History tab.** `#tab-history` opens `#panel-history`, which holds `#run-history-list` (`role="group"`, labelled `HISTORY_LIST_LABEL`). It is drawn from a fresh `readLog` by `render()` with `createElement` and `textContent`: when the tab is shown (`mountTabs`' `onShow` calls `runLog.refresh()`), and after every run and every database load while it is the selected tab (`isShown()`); an empty log shows one `<p class="run-history-empty">`. One real `button.run-history-entry` per entry, newest first: the first non-blank line of the SQL in the code typeface (cut at `HISTORY_SQL_PREVIEW_CHARS` = 80, with an ellipsis also when more lines follow), then the UTC date and time with the word "UTC" after it (`HISTORY_TIME_ZONE`) and the outcome (`12 rows`, or an icon and the word `Error`). The SQL is never put in an attribute. The list is one Tab stop (roving tabindex); ArrowDown, ArrowUp, Home and End move through it; Enter or a click puts the SQL in the editor (`editor.value = sql`; nothing runs, nothing is saved as the last query), says `HISTORY_RESTORED_MESSAGE` in a toast (the result on screen stays, with its summary line) and focuses the editor. It is a tab panel, not a popup, so nothing closes it. Its colours are the tokens of `css/tokens.css` (`--danger` for an error), all checked at 4.5:1 by `tests/ui1-tokens.spec.js`.

### 9.2 The file and its verification (`evidence.js`)

```
<APP_NAME> evidence export v1
dataset: <log key, control characters as "_">
exported: 2026-11-09T14:32:08Z
<blank>
[1] 2026-11-09T13:58:12Z · 12 rows            ("1 row", "0 rows", or "error: <message>"; the dot is U+00B7)
<the SQL, newlines normalised to LF; a line that has the shape of an entry header gets a backslash in front>
link: <F3 link>                                (only for a successful entry on a built-in dataset)
<blank>
[2] ...
<blank>
student: <student number>
sha256: <64 lower-case hex digits>
```

LF only; entries oldest first, numbered from 1; one LF after the `sha256:` line. `sha256` is `crypto.subtle.digest("SHA-256")` over the UTF-8 bytes (`TextEncoder`) of everything up to and including the LF of the `student:` line. `formatEvidence({entries, dataset, exported, student})` builds the signed part (throws `RangeError` for no entries or a student number that would not stay on one line); `buildEvidence` adds the checksum line. CRLF and lone CR in SQL become LF before writing, and `escapeSql` puts `EVIDENCE_SQL_ESCAPE` (a backslash) in front of every SQL line that matches the header shape (`[n] <timestamp> · <k> row(s) | error: ...`), so in a file this exporter wrote the header-shaped lines are exactly the real entries (the entry's `link:` holds the exact SQL).

`verifyEvidence(text)` is async, never rejects, and returns `{status:"valid", student, queries, exported, dataset}`, `{status:"edited", reason}`, or `{status:"unavailable", reason}` when `crypto.subtle` is missing (checked first: neither word can then be said). Rules, in order: not a string -> edited; over `EVIDENCE_MAX_BYTES` (20 MiB) characters -> edited; blank -> edited; CRLF becomes LF and nothing else is normalised (a lone CR stays, so an LF changed to CR is caught); two LFs at the end -> edited (when the last line before those line breaks is not a checksum line the reason is "There is extra text after the checksum line."; otherwise the file is checked with one LF at the end, and `VERIFY_EXTRA_BLANK_LINES_REASON`, "Extra blank lines were added after the checksum line.", is the reason only if it would then be VALID, so a file whose contents were changed too gets the reason it really fails with), one is stripped; fewer than 9 lines -> edited; the last line must match `^sha256: [0-9a-f]{64}$` (upper case refused); the line before it must be `student: ` plus a non-empty value (`STUDENT_ID_PATTERN` is deliberately not applied, so changing it does not invalidate older files); the recomputed checksum must match; then the first line must end in ` evidence export v1` (any app name, so a rename does not invalidate older files), line 2 `dataset: <non-empty>`, line 3 `exported: <a real UTC timestamp>`, line 4 blank. The query count is the number of lines that follow a blank line, match `[n] <timestamp> · (<k> row(s)|error: ...)` and are numbered 1, 2, 3 ... in sequence; at least one is required. The order is on purpose: a damaged footer is named as such, any other edit reports "the checksum does not match". Reason texts never contain the words VALID or EDITED. Because the exporter escapes header-shaped SQL lines, the count of a genuine file is exact, whichever entry the SQL is in. Known limit: a file that was not written by this exporter (or was written and re-signed by hand) can hold unescaped header-shaped lines, and a blank line followed by a next-in-sequence header inside an entry is then counted; the checksum only says the file is as it was written, and anyone who wants to forge a count can write the whole file (deterrence-grade, spec 5a).

### 9.3 The export dialog (`evidence-dialog.js`)

"Evidence (.txt)…" (`#export-evidence`) in the Export menu (`export-menu.js`) calls `evidence.open()`; `mountEvidence({runLog, returnFocus})` -> `{open()}` takes `#export-button` as `returnFocus` and builds no button of its own. Opening: an empty log -> a toast says `EVIDENCE_EMPTY_MESSAGE`, no dialog; no `crypto.subtle` (an insecure origin) -> a problem toast says so, no dialog; otherwise `#evidence-dialog` (a real `<dialog>`, `showModal`, drawn as `.app-dialog` like the database export) opens: the title "Export evidence", the plan's one sentence (`EVIDENCE_DIALOG_TEXT`, "Creates a text record of the queries you ran, to attach to your assessment.", also the dialog's `aria-describedby`), a labelled input (`autocomplete="off"`, no `name`, no `maxlength`, so a too-long number can be typed and refused), a hint (which says the number goes in the file and nowhere else), `#evidence-error` (`role="alert"`), and `#evidence-file`, the file it will save ("Saved as evidence-northlight.txt", named before Export is pressed), then Export (`button--primary`) and Cancel. The number is checked exactly as typed (no trimming) against `STUDENT_ID_PATTERN`; a bad one sets `aria-invalid` and `aria-describedby="evidence-error"`, keeps the dialog open and the focus in the input. The hint and invalid-number wording (`EVIDENCE_HINT`, `EVIDENCE_INVALID_MESSAGE`) are separate constants: change them with the pattern. A good one: the log is read again, each entry gets `link: <url>` if `linkFor(key, entry)` says so, `buildEvidence` runs, `saveFile` saves `evidence-<safeBaseName(log key)>.txt` (`evidence-northlight.txt`, `evidence-file_hw.db.txt`), the dialog closes, focus returns to `#export-button` and a toast says what was saved ("Exported evidence-northlight.txt with 3 queries"; a failure is a problem toast, with no detail). **A cancelled export stays cancelled.** The checksum is made asynchronously, so `exportNow` takes `exportToken` when it starts, and every way of closing (`closeDialog`, the dialog's `cancel` event for Escape, and `close` when the dialog is not open again) changes it; after the `await` the file is saved only if the token is unchanged. `dialog.open` alone was not enough: cancel, then reopen before the checksum finished, and the old export completed into the new dialog (tests `an export cancelled with Cancel|Escape while its checksum is made ...`).

**The student number goes nowhere but the file**: not storage, an address, the file name, the title or the console (the catch blocks log nothing); the input is emptied on `cancel`, by `closeDialog()` and on `close`. An export that is cancelled while it makes its checksum is stale (the token changed) and no longer counts as busy (`busyToken`), so a new submit right after is not ignored; the stale one saves nothing. A test dumps storage, URL, title, HTML, text, cookies, console and requests for a 12-character number and finds it only in the file.

`linkFor(key, entry)` is null for an error entry, for a `file:` key (an upload or URL database cannot be reopened from a link), and when the F3 fragment is null (payload too long) or `decodeShare` would refuse it; otherwise it is the page URL with its query removed and the fragment for that dataset and SQL alone (no exercise set).

### 9.4 `verify.html` (`verify-page.js`)

Brand, credit footer, a link back to `./`, a labelled `<textarea id="evidence-text">`, `#verify-button`, a real `<input type="file" id="evidence-file">`, a drop zone (a drop is taken anywhere on the page and always `preventDefault`ed), and `#verify-result` (`role="status"`, always in the layout). It checks on paste, drop, file choice and Verify. The result is built with `createElement` and `textContent`: VALID (a definition list of student number, queries, exported, dataset, and a note that it does not prove who ran the queries), EDITED with the reason, or, without `crypto.subtle`, a message that says neither. A file over 20 MB is refused by its `size` before it is read. Only the newest check may show its result (a ticket counter). The page lists no entries and no links (spec 5a asks for the verdict only, and a list would put text from the file on the page for no gain: the marker uses the `link:` lines in the `.txt`). After each check it calls `scrollIntoView({block: "nearest"})` on `#verify-result`, because the verdict sits below the box and was off screen in short windows. `about.html` (section "For markers") points markers here; the app's own pages do not otherwise link to it.

**The paste problem.** `textarea.value` turns a lone CR into LF, which would hide an LF changed to CR. The paste handler therefore reads `clipboardData.getData("text/plain")`, verifies that raw text, puts it in the box itself (`preventDefault` + `setRangeText`) and remembers `{raw, value}`; Verify uses the raw text until the next `input` event, and the box's value after that. A paste that replaces part of the box is spliced into the raw text through `rawIndex`. In tests a paste is a synthetic `ClipboardEvent` whose `DataTransfer` is filled after the event is made (Firefox ignores one filled beforehand). A leading BOM added to an evidence file is not detected when the file is chosen or dropped, because `File.text()` drops it and the text is the same; only the pasted route can see one.

## 12. localStorage

Complete list. `js/`, `index.html`, `about.html` and `verify.html` store nothing in `sessionStorage`, IndexedDB or a cookie (`js/lab/storage-guard.js` only reads the `window.localStorage` and `window.sessionStorage` properties and, where reading one throws, redefines it as undefined; it never reads or writes an item), and the student number of the evidence export is in none of them (section 9.3). The engine opens `:memory:`, so SQLite persists nothing (the build also registers `kvvfs`, a localStorage-backed VFS, which nothing opens).

| Key | Value | Written by | Removed by |
|---|---|---|---|
| `sqlime.query.<database name>` (`storage.js`; the upstream name is kept so saved queries survive) | The last SQL run for that database name (the file basename, or `new.db`; two databases with one basename share a slot). | `execute` (every run with persist on, the trimmed text that was run); `changeName` (the rename in the export dialog) moves what is saved under the old name to the new one without writing `database.query`, so renaming never saves SQL that was not run. | `changeName` (old name); `set` with empty SQL calls `remove` and then still writes `""`. With storage unusable, writes land in memory. |
| `sqllab.progress.<set id>` (`PROGRESS_PREFIX`) | `{v: 1, passed: {<exercise id>: true}, drafts: {<exercise id>: "<sql>"}}` | `markPassed`, `saveDraft` (section 7.3) | `resetSet` |
| `sqllab.log.<log key>` (`RUN_LOG_PREFIX`) | `{v: 1, entries: [{t, sql, rows} or {t, sql, error}]}`, at most 200, oldest first; the log key is the dataset id or `file:<database name>` | `appendLog` on every Run | nothing; the cap drops the oldest |
| `sqllab.theme` (`THEME_STORAGE_KEY`) | `"light"` or `"dark"`; no key means match the device | `setThemeChoice` (the Theme menu); read by `theme-boot.js` before the first paint | `setThemeChoice("device")` |
| `sqllab.textSize` (`TEXT_SIZE_STORAGE_KEY`) | The size of the SQL and the results in px, one of `TEXT_SIZES` (12 to 24, even); anything else is ignored for 14 | `mountTextSize` (A− and A+); read by `theme-boot.js` before the first paint | nothing |
| `sqllab.layout` (`LAYOUT_STORAGE_KEY`) | `{v: 1, sidebar, collapsed, editor}`: the sidebar's width in px (220 to 420), whether it is hidden, and the editor pane's share (its toolbar and the editor) of the room under the exercise prompt (a fraction, 0.05 to 0.95 exclusive); a value outside those ranges, or JSON of another shape, is ignored for the default | `mountLayout` (after a key on a splitter, at the end of a drag, on a double click on the sidebar's splitter, and when a set opening brings a hidden sidebar back) | nothing |

The `sqllab.*` prefixes are storage namespaces, not branding: they deliberately do not follow `APP_NAME`, so renaming the app does not orphan saved progress or logs (`m2-brand.spec.js` lists them as the only other places the old spelling may appear). Upstream also wrote `github.username` and `github.token`; nothing reads or writes them now. New keys use the `sqllab.*` prefix. Spec constraint 4: localStorage only for history and progress, no cookies, no analytics; the UI plan adds display preferences on top (the theme, the layout and the text size), never anything a student wrote.

## 13. Engine and platform facts

- **Engine.** The official SQLite WASM build (`jswasm` `sqlite3.js` + `sqlite3.wasm`, `oo1` API), 3.54.1, not sqlean: no extensions beyond what the stock build compiles in. Raw 439,732 B + 879,430 B, about 1.3 MB of the 3 MB budget (the editor's CodeMirror bundle adds about 0.4 MB, the typefaces 0.17 MB). Loaded as a classic script on the main thread, then `sqlite3InitModule(CONFIG)` in `manager.js`; the `.wasm` is fetched relative to the script, always: `vendor/sqlite3.js` would take another place from the query parameters `sqlite3.dir` and `sqlite3.wasm`, so `js/lab/engine-guard.js` removes every `sqlite3.*` parameter from the address before the engine script runs (a crafted link cannot make the page fetch and run the engine from another host). No Web Worker.
- **No COOP/COEP dependency.** Nothing uses `SharedArrayBuffer`, `Atomics`, OPFS, `crossOriginIsolated` or `Worker`. Without special headers `crossOriginIsolated` is false, `SharedArrayBuffer` is undefined, `sqlite3.opfs` is undefined and the app works (`smoke.spec.js`). The working database lives in memory; saving is the export download.
- `sqlite3InitModule` is **single-use**: a second call throws. `manager.js` caches the result and keeps the API object private; new code must not boot a second engine. Get connections from `manager.init(name, path)`.
- `database.db.constructor` is not `sqlite3.oo1.DB`; build connections through `manager.init`, and use `database.capi` / `database.db` (not `database`'s module-private variable) from lab code.
- `crypto.subtle` needs a secure origin (https or localhost). Evidence export and `verify.html` say so instead of failing silently.

## 14. Untrusted text

Everything from a database, file, file name, URL, share link, manifest, exercise file or error is untrusted. Build DOM with `createElement` and `textContent` (or `dataset`), or pass the string through `escapeHtml` before any `innerHTML` (`sqlime-result`'s unused `print` writes innerHTML through `printer.js`, which escapes; the results pane, the toasts and the dialogs use `textContent` only). Names are put in SQL only through `js/lab/sql.js` (identifiers quoted, quotes doubled; replacement is by function so `$&` is not a pattern). `SQLite.getTableInfo` still has a raw splice; nothing calls it. File names reach the page only through `textContent` (the switcher's button, the status bar), the export dialog's input `value`, `document.title` and storage keys. Tests: `m2-injection.spec.js`, `m2-table-names.spec.js`, `m3-schema.spec.js` (hostile identifiers and manifest), `m4-panel.spec.js` (hostile set content), `m5-verify-page.spec.js`, `m5-evidence-dialog.spec.js`.

## 15. Extending

- **A feature module.** Put it in `js/lab/`, export a `mount...` function, add a one- or two-line seam in `js/index.js` that calls it, and follow the page through `lab:database-loaded` / `lab:run-finished`. Put texts and constants in `config.js`. Do not edit `js/sqlite/`.
- **A button in the editor toolbar.** Append a `<button class="button">` to `#editor-toolbar` (insert it after a known sibling, as Check answer goes right after `#execute`; one filled `button--primary` per context). Buttons using `data-action` get `ActionController`, which listens on `.topbar` and `#editor-toolbar` (handlers return a Promise and the button is disabled until it settles); otherwise attach a plain listener. The toolbar wraps, so check it at 360px.
- **A top bar control.** Append to `.topbar-actions` (a menu: the next item); the bar wraps at every width. A sidebar tab: a `button[role=tab]` with `aria-controls` in `.tabs` and a `div.tab-panel[role=tabpanel][hidden]` after it in `nav#sidebar`; `mountTabs` takes the tabs from the tablist, so no JavaScript changes, and the panel's stylesheet `<link>` goes next to its markup.
- **A panel.** A new row of the main area needs a grid area in `css/shell.css` (`.main` has prompt, toolbar, editor, splitter and results; `layout.js` observes every child of `main#main` except the editor pane, the results pane and the splitter, so a new row reflows the editor's height), with its own stylesheet `<link>` next to its markup in `index.html`.
- **A shortcut.** A second `new ShortcutController({...}).listen(document)`, or a capture-phase `keydown` as the Check shortcut does. Ctrl/Cmd+O, U and Enter (and Shift+Enter while a set is open) are taken, and in the editor so are `/` (comment), Space with Ctrl (completion), Z and Y (undo, redo) and the rest of CodeMirror's default keymap; avoid `s` (browsers bind it to Save). A key for the editor alone goes in `code-editor.js` (a keymap entry), not on the document.
- **Changing the editor.** `index.js` and the lab modules touch the editor only through the surface of 4.5 (`value`, `query`, `focus()`, `setSchema`, `view`/`code` in `caret.js` and `insert.js`, the `input` / `execute` events), plus the id `#editor`. A CodeMirror extension goes in `extensions()` of `code-editor.js`; a CodeMirror piece not yet bundled is added to `tools/editor-entry.js`, then `npm run build:editor`. Keep "selection else all" for `.query` (selections outside the editor ignored), the Escape-then-Tab way out, the `aria-describedby="editor-hint"` link (`m2-editor-keys.spec.js`, `ui3-editor.spec.js`) and the plain box working on its own.
- **A dataset or exercise set.** Section 6.3 and 7; the README has the instructor's version.
- **A storage key.** Section 12; own module, own `sqllab.*` prefix, every access in try/catch, memory fallback.
- **A colour.** Only in `css/tokens.css`: the light value on `:root` and the dark one in both dark blocks; add any new text-on-surface pairing to `PAIRS` in `tests/ui1-tokens.spec.js`.
- **An icon.** `icon("name")` with the literal Lucide name, then `node tools/build-icons.mjs` (after `npm ci`) to rewrite the sprite in `index.html`.
- **A menu.** A `<button>` and, right after it, an element with an id, `role="menu"` and items (`role="menuitem"` / `"menuitemradio"`, `tabindex="-1"`), then `mountMenu(button, menu, {onSelect})` (`js/lab/menu.js`; `theme.js` is the example). Styles: `.menu`, `.menu-item`, `.menu-separator` in `css/menu.css`.
- **Branding.** The app name only through `config.js`: `data-app-name` in HTML, `APP_NAME` or `titleFor` in JS. A test fails if the name is written anywhere else in shipped HTML, CSS, JS or SVG.

## 16. Decisions, known quirks, not built

**Not built, on purpose.** Spec F9 (hidden-answer exercises storing a result fingerprint instead of the model query) and F10 (printable worksheet) are P2 and belong to no milestone; the model query is readable in the fetched JSON. (F8, CodeMirror with highlighting and autocomplete, came with the UI plan's Phase 3, section 4.5.) Out of scope per the spec: any backend or accounts, grade export or LMS integration, DML/DDL exercises, engines other than SQLite, AI query help, saving databases anywhere but the user's own file download.

**Decisions** (each is explained where it appears): restored SQL never runs, and since the UI plan's Phase 4 nothing runs on load at all (4.1); a Run waits one frame so "Running…" can show during a long one (4.2); toasts answer actions, bands hold problems that must stay (8); the model query is private to the checker; per-exercise saved SQL lives in the progress record (7.3); exercise sets are discovered through a deploy-time folder listing (7.1); student SQL runs under the guard in `runner.js` (5); the run log is per dataset and its key is fixed when the database opens (9.1); the student number goes only into the file, and the verify page ignores `STUDENT_ID_PATTERN` and the app name so older files verify (9.2); CSV cells are not escaped and a BOM is added only for non-ASCII (8).

**Known quirks and dead code.** `DatabasePath.toHash`, `SQLite.getTableInfo`, `SQLite.execute`, `MESSAGES` (`js/sqlite/db.js`: the old status texts), `tableInfoSql` (`js/lab/sql.js`), `QUERIES.tableContent` (`js/sqlite/db.js`: the old table preview's query), `print` and `printTables` (`sqlime-result.js`, `printer.js`: the result table is `js/lab/result-table.js` since Phase 4, and `printTables`' buttons carry `data-action="showTable"`, which nothing handles), and the editor's `start` event (nothing listens) are unused. A Run in exercise mode writes the free-query slot (7.3). `execute` has no timeout, so a runaway query hangs the tab (as upstream).
